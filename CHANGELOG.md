# Changelog

## 5.8.0 — Unreleased

- `project init` now refuses an `advisor_policy` action that the Advisor would discard on every review, such as one whose outcomes all lead to the same `next_decision`, one with fewer than two competing explanations, or one without required observables. The rejection names the action and the Advisor's own reason. The owned context freezes with the contract, so before this such an action was frozen in, silently dropped from every `advise` and `project advance` (`selected_run: null` when it was the only route), and could be corrected only in a new project root. Init uses the Advisor's own admission check, so actions it admits are unchanged, and nothing is written on the rejection.
- `project init` now refuses a protocol binding whose declared `code_sha256`, `config_sha256` or `data_sha256` conflicts with the contract's bindings, with the same message `project create` gives plus the protocol path. The protocol file freezes with the contract, so before this the conflict surfaced only at the first registration, when the file could no longer be corrected: correcting it changed its hash (`Binding changed`), and re-initializing gave `Contract is frozen; use a new project root`. Nothing is written on the rejection, so the same root can be corrected and initialized. Protocol files that are not JSON, or that declare none of these hashes, initialize as before, and registration keeps its full identity check. (#154)
- `Protocol identity conflicts with bindings` now names the conflicting role, the expected value and the rule (#154): with one binding for `code`, `config` or `data` it is that file's SHA256, and with several it is the canonical digest of the role's `{path, sha256}` bindings sorted by path. Before, the rejection gave none of these, and the examples only show the single-file case, so projects with a second source file could not tell what to write. The check, its strictness and what registers are unchanged.
- `checkpoint save` now refuses a route decision that loop-history review would always refuse (#153). This covers a decision with `question_id` and all of `goal_revision`, `scope`, `candidate`, `outcome` and `evidence` whose candidate is a plain string or lacks a structured action, or whose outcome or scope is invalid. Before, the record was saved and checkpoints are append-only, so every later review of that question returned `LOOP_HISTORY_REVIEW_ERROR` and `advise`/`project advance` were rejected for good. Writer and reader now share one validator, and `checkpoint save` writes nothing on the rejection. A record whose JSON nesting review cannot parse, which would block every question, is refused the same way, and so is a declared-domain rejection whose witness path is not absolute. Opaque notes without the route fields save as before. The launch rejection `Repair checkpoint integrity before executing a candidate` now includes the review's reason.
- Pass the live contract and its matching digest into owned Advisor loop review, so the first valid checkpoint no longer blocks subsequent `advise` or `project advance`. Keep checkpoint hash and contract checks intact; tampered or foreign-contract records still reject before launching or charging a run. Real CLI regressions cover empty and structured checkpoint decisions. (#149)
- Reuse an identical concurrent owned dependency-map publication after locked ledger validation, so a late duplicate registration cannot prevent the valid registered run from advancing. Reuse is limited to one direct publication with the same map and source base and no declaration revision; stale graph changes, revisions, admission checks and duplicate run IDs still reject. Real CLI timing gates cover one launch, receipt and budget charge. (#144)
- Keep theory progression UNKNOWN when any required native leaf lacks accepted status, assurance or a bound certificate, independently of absent/null/empty/non-string diagnostics. Stop dispatch on the first unaccepted leaf and count only accepted proofs in `pairs_checked`; the faithful CLI regression returns 2 for UNKNOWN. Native proof budgets and scientific/application UNKNOWN are unchanged. (#141)
- After `math bind` on a root without `project init`, `advise --choose … --record`, `project status`, `project next` and other project-contract readers now reject with `Project contract has not been initialized`, as on an empty root (#135). `project next` keeps its `project init` hint. Before, they failed with `[RDS-ERROR] OperationalError: no such table: contract`, because the bound objective shares `.rds/project.sqlite3` and the contract reader did not check for the table. Nothing is written on the rejection, and the bound objective is unchanged. `advise --record` now reads the contract before storing the advice in CAS, so a rejected record no longer leaves an advice blob under `.rds/cas`, on an empty root as well. A contract table without a row is still `Project contract is missing`, and `project next` gives it without the init hint.
- Add a bounded real-CLI progression for one fixed finite rational multiplication claim, binding the existing exhaustive Cayley check, non-certifying EGraph rewrite check and native Lean closed-rational leaves to the same declaration. Preserve stage evidence, assurance, work limits and hash-bound handoffs; missing Lean, unsupported input and incomplete stages remain UNKNOWN. This proves only the listed finite instances, not an application result or a scientific claim. (#53)
- The shared receipt read behind `hypergraph --audit-receipts`, `advise` (dependency map and obstruction audit) and the `exec` goal-link guard now applies the project ledger's own receipt check (#118, #104). Before, it used a permissive decode, so a row that `project status` rejects could still ground evidence: a FAILED receipt with a second `run_status: SUCCEEDED` key, a FAILED receipt edited to SUCCEEDED but keeping its recorded sha256, or a receipt naming another run. Each was `GROUNDED`, and the goal became `DECLARED_SUPPORTED`. Such a row is now `RECEIPT_BODY_INVALID`, and its `reason` gives the owner's failure: `repeats a JSON key`, `names a different run`, `does not match its recorded sha256` or `has no canonical encoding (…)`. Nothing is read out of it, so the record stays in `receipt_blocked_node_ids`, and an obstruction gives `DISCRIMINATING_CHECK` with cause `UNKNOWN`. A body whose `sha256` field differs from its row was `RECEIPT_BODY_MISMATCH` in the obstruction audit and `RECEIPT_NOT_SUCCEEDED` in the map. It is now `RECEIPT_BODY_INVALID` in both. Ambiguous rows, non-text columns, non-object bodies, malformed JSON (`LEDGER_UNAVAILABLE`) and writer receipts read exactly as before. The named ledger is only read. A grounded receipt still records execution, not statement truth.
- Keep whitespace-padded `UNKNOWN` protocol identities unresolved in control reuse and receipt/cost validation (#131). Classify missing values from stripped text, including nested lists and dictionaries, while retaining exact comparisons for real known identities. Real CLI regressions preserve `scientific_assessment=UNKNOWN`; no cached control is executed or historical record rewritten.

- Accept only RFC 6901 tilde escapes (every `~` followed by `0` or `1`) in artifact JSON and JSONL pointers (#115, #84). One value could therefore affirm several Triple Affirmative predicates under different locators. These spellings now leave the fact UNKNOWN with the existing `invalid JSON pointer escape` reason. The whole pointer is checked before any segment is read, so a missing key earlier in the pointer no longer decides the reason. Guard metric pointers share this reader, and the same malformed spellings there are now UNKNOWN. Valid pointers, their decoding and their locators are unchanged.

Counts remain recorded invocations; a later enabled logger cannot establish complete historical coverage. They now leave the fact UNKNOWN with `JSONL row is a 1-based physical line number`; string, zero, negative and missing rows were already UNKNOWN and now give the same reason. - A damaged receipt row in the project's own ledger is now rejected as `[RDS-REJECT] Project receipt integrity failure: run <id> body …; inspect retained state`. This covers a body that is not valid JSON (including too-deep nesting), repeats a JSON key, is not a JSON object, names a different run, does not match the `sha256` recorded in its row, or has no canonical encoding (a `NaN`/`Infinity` or overflowing float, or an unpaired surrogate escape: the decoder accepts these, the writer never emits them); the recorded `sha256` field is compared before this re-encoding. The digest the writer already stores is recomputed on each read. The rejection applies to `project status --brief`, `next`, `execute` (the `execution_policy` observation), `recover`, `create` (maintenance spend) and other project-snapshot consumers. At the claim of a maintenance or stop-policy run, it propagates and is not recorded as that run's admission failure; the claimed run stays reserved and unsettled. A later integrity rejection at the pre-start recheck keeps the attempt and unknown costs unsettled, rather than manufacturing a FAILED receipt; restoration followed by recovery reconciles the same attempt without another launch. Before, `execute` and `recover` crashed with an `AttributeError` traceback, and status reads printed a bare Python message. `recover` also returned an id-less, mislabeled or edited body with exit 0, and `next` proposed executing a run that had already finished. Reads and the claim write nothing on a rejection, and valid ledgers read exactly as before. (#104)
